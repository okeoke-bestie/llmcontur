# LLM-контур первичной обработки заявок о неисправностях

Сервис принимает заявки из хелпдеска и для каждой делает одно из трёх:

- **Автозакрытие.** Если проблема типовая, пользователю уходит выверенная инструкция из каталога.
- **Эскалация.** Заявка уходит инженеру вместе с технической переформулировкой, категорией и причиной эскалации.
- **Ручной режим.** Если провайдер LLM недоступен или модель ответила невалидно, заявка обрабатывается вручную, как было до автоматизации.

Модель **не пишет инструкции сама**, а только выбирает одну из каталога, который ведут инженеры. Свободная генерация текста инструкций по починке — надёжный способ уверенно посоветовать пользователю что-нибудь удалить.

## Архитектура

```
 Хелпдеск ──webhook──► POST /tickets ──► SQLite (идемпотентно по ticket_id) ──► asyncio.Queue
                                                                                    │
                                                                         N воркеров │
                                                                                    ▼
      ┌──────────────── TriageService ────────────────────────────────────────────────┐
      │ 1. Гибридный поиск по каталогу (BM25 + TF-IDF триграмм, RRF) → top-k кандидатов │
      │ 2. Промпт (версионируется) → Mistral, JSON mode, temperature=0                │
      │    ретраи с экспоненциальным бэкоффом на 429/5xx/таймауты                      │
      │ 3. Валидация по pydantic-схеме                                                 │
      │ 4. instruction_id ∈ кандидатов и категории совпадают, иначе эскалация          │
      │ 5. Risk-guard: деньги / безопасность / массовый сбой / интеграции → человеку   │
      │ 6. Порог уверенности → auto_resolved | escalated                               │
      └────────────────────────────────────────────────────────────────────────────────┘
                                                                                    │
                          results + audit_log (промпт, кандидаты, сырой ответ, версия)
```

| Модуль | Что делает |
|---|---|
| `app/triage.py` | Основной пайплайн: ретраи, деградация, валидация, решение |
| `app/retrieval.py` | Гибридный поиск без внешних зависимостей (в проде заменяется на эмбеддинги + pgvector) |
| `app/prompts.py` | Промпт и `PROMPT_VERSION` |
| `app/guards.py` | Детерминированные правила, которые модель не может обойти |
| `app/llm/` | Клиент Mistral и офлайн-`MockLLM` для разработки, тестов и CI |
| `app/storage.py` | Заявки, результаты, аудит-лог |
| `app/metrics.py` | Доля автозакрытий, доля возвратов, время до первого ответа |
| `eval/` | Золотой набор и регрессионный прогон |
| `scripts/` | Генерация истории, анализ «до кода», симуляция пилота |

## Быстрый старт

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env            # без ключа работает офлайн-mock
uvicorn app.main:app --reload
```

```bash
curl -X POST localhost:8000/tickets -H 'Content-Type: application/json' \
  -d '{"ticket_id":"T-1","user_id":"u1","body":"после обновления приложение вылетает при запуске"}'
curl localhost:8000/tickets/T-1          # решение, категория, переформулировка, ответ пользователю
curl localhost:8000/tickets/T-1/audit    # промпт, кандидаты, сырой ответ модели, версия шаблона
curl localhost:8000/metrics
```

**Реальная модель.** Запишите ключ из [console.mistral.ai](https://console.mistral.ai/) в `.env` как `MISTRAL_API_KEY=...`. При `LLM_PROVIDER=auto` сервис сам переключится на Mistral.

**Docker.** Выполните `cp .env.example .env && docker compose up --build`.

## API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/tickets` | Вебхук хелпдеска (202; повтор с тем же `ticket_id` вернёт `duplicate: true`) |
| GET | `/tickets/{id}` | Статус и результат |
| GET | `/tickets/{id}/audit` | Полный след вызова модели |
| POST | `/tickets/{id}/engineer-reply` | Отметка первого ответа инженера (для метрики времени ответа) |
| GET | `/metrics` | Продуктовые метрики |
| GET | `/catalog`, `/health` | Каталог и состояние |

Если задан `WEBHOOK_TOKEN`, запросы на запись требуют заголовок `X-Webhook-Token`.

## Качество

```bash
make test       # 21 тест: ретраи, деградация, отказ от несуществующих id, идемпотентность, метрики
make eval       # золотой набор; exit 1 при регрессии относительно eval/baseline.json
```

Каждую правку промпта, порога или каталога прогоняют через `make eval`, иначе изменение формулировки незаметно ломает соседние категории. Регрессией считаются:

- падение `auto_precision`, `category_acc` или `auto_coverage` больше чем на 2 п.п.;
- любая `critical_error`, то есть нетиповая заявка (оплата, безопасность, инцидент), закрытая автоматически.

Главная продуктовая метрика — **доля возвратов**: пользователь, получивший автоответ, снова пишет по той же категории в течение 72 часов. Фиктивное автозакрытие хуже, чем отсутствие автоматизации, поэтому в `/metrics` есть и `net_auto_resolution_rate`, то есть доля автозакрытий за вычетом возвратов.

## Анализ и пилот на истории

```bash
make data       # data/history.jsonl — 3000 синтетических заявок
make analyze    # покрытие типовыми инструкциями и экономика: инференс против часов инженеров
make simulate   # прогон 500 заявок: доля автозакрытий и время первого ответа до/после
```

> **Важно.** `data/history.jsonl`, `eval/golden.jsonl` и цифры, которые выдают `analyze` и `simulate`, **демонстрационные**: данные синтетические и сгенерированы так, чтобы показать работу контура. Метрики `MockLLM` на золотом наборе — это smoke-тест пайплайна, а не качество модели. Реальные цифры получаются только на реальных данных и с реальной моделью.
